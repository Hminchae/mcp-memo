LLM에게 작업 지시서, 도구, 세션, 워크스페이스, 정책을 붙여 에이전트처럼 일하게 만드는 실행 프레임워크 

그래서 오픈클로 자체의 동작에 어떤 방법으로 위 기능이 가능한지 궁금


Telegram
→ bot.py
→ Orchestrator /generate
→ Ollama
→ Telegram 응답




# 1. 현재 구조에서 LLM 호출 사이클

현재 `bot.py` 기준으로 보면 흐름은 이거야.

```
사용자 Telegram 메시지→ bot.py의 handle_text()→ build_gx10_prompt()→ call_orchestrator()→ POST /generate→ Orchestrator가 Ollama 호출→ qwen2.5-coder:7b가 답변 생성→ Orchestrator 응답 반환→ bot.py가 Telegram에 답장
```

조금 더 풀면:

```
1. 사용자가 Telegram에 메시지를 보냄2. Telegram Bot API가 메시지를 보관함3. bot.py가 long polling으로 메시지를 가져옴4. bot.py가 메시지가 /health 같은 command인지 일반 텍스트인지 판단함5. 일반 텍스트면 GX10 시스템 프롬프트를 붙임6. Orchestrator의 /generate API로 prompt를 보냄7. Orchestrator가 gx10-llm-01의 Ollama API를 호출함8. Ollama가 qwen2.5-coder:7b 모델로 텍스트를 생성함9. 결과가 Orchestrator → bot.py → Telegram 순서로 돌아옴
```

현재는 여기까지야.

---

# 2. 현재 구조로 “챗봇 CRUD 만들어줘”라고 하면

현재는 아마 이런 식으로 동작해.

```
사용자:간단한 챗봇 CRUD 만들어서 로컬 서버에 띄워줘bot.py:이 문장을 GX10 컨텍스트와 함께 /generate로 전송Orchestrator:Ollama에 prompt 전달LLM:"간단한 FastAPI CRUD 예시는 다음과 같습니다...""로컬 서버에 띄우려면 uvicorn main:app --reload를 실행하세요..."같은 답변 생성Telegram:답변 표시
```

즉 현재는 **코드 설명/생성 텍스트**는 가능하지만, 실제로:

```
파일 생성패키지 설치서버 실행포트 오픈상태 확인URL 반환
```

은 아직 자동으로 하지 않아.

# 3. 최종 구조에서의 사이클

네가 만들고 싶은 “개발 자동화 Agent” 기준으로는 한 번의 요청이 여러 번의 LLM 호출과 여러 번의 Worker 실행으로 쪼개져야 해.

예시 요청:

```
간단한 챗봇 CRUD 만들어서 로컬 서버에 띄워줘
```

최종 사이클은 이렇게 가는 게 맞아.

```
Telegram→ Gateway / bot.py→ Orchestrator→ Policy Engine→ OpenClaw Planner Agent→ Worker Sandbox→ OpenClaw Reviewer Agent→ Approval Flow→ Worker 실행→ 결과 반환
```

---

# 4. 전체 흐름 그림

```
[User]  |  | Telegram 메시지  v[bot.py / Gateway]  |  | InternalMessage 변환  v[Orchestrator]  |  | 작업 분류  v[Policy Engine]  |  | "코드 생성 + 서버 실행"은 위험 작업인가?  v[OpenClaw Planner Agent]  |  | LLM 호출 1: 작업 계획 생성  v[Orchestrator]  |  | 승인 필요 여부 판단  v[Telegram]  |  | 사용자 승인  v[Worker Sandbox]  |  | 파일 생성 / 패키지 설치 / 서버 실행  v[OpenClaw Reviewer Agent]  |  | LLM 호출 2: 결과/로그 해석  v[Telegram]  |  | 실행 결과 반환
```

---

# 5. 실제 사이클을 단계별로 보면

## Step 1. Telegram 메시지 수신

사용자가 Telegram에 보냄.

```
간단한 챗봇 CRUD 만들어서 로컬 서버에 띄워줘
```

`bot.py`가 이 메시지를 받음.

현재는 여기서 바로 `/generate`로 보내지만, 확장 구조에서는 먼저 공통 메시지로 변환해야 해.

```
{  "channel": "telegram",  "user_id": "123456789",  "chat_id": "987654321",  "text": "간단한 챗봇 CRUD 만들어서 로컬 서버에 띄워줘"}
```

이걸 Orchestrator로 넘김.

---

## Step 2. Orchestrator가 작업 종류 분류

Orchestrator가 먼저 이 요청을 분류해야 해.

```
이 요청은 단순 질문인가?코드 생성 요청인가?실제 실행 요청인가?서버 실행 요청인가?승인 필요한가?
```

이 요청은 단순 질문이 아니야.

```
코드 생성 + 파일 생성 + 서버 실행
```

이 포함되어 있음.

그래서 Orchestrator는 이렇게 판단해야 해.

```
{  "intent": "dev_task",  "task_type": "create_local_app",  "requires_planning": true,  "requires_worker": true,  "requires_approval": true}
```

왜 승인 필요냐면:

```
- 파일을 생성해야 함- dependency를 설치할 수 있음- 로컬 서버 프로세스를 띄워야 함- 포트를 점유함
```

그래서 자동으로 바로 실행하면 안 됨.

---

## Step 3. OpenClaw Planner Agent 호출

이제 Orchestrator가 OpenClaw를 호출함.

이때 LLM 호출이 한 번 일어남.

```
Orchestrator→ OpenClaw agent→ Ollama qwen2.5-coder:7b
```

프롬프트는 대충 이런 구조가 됨.

```
너는 GX10 개발 자동화 Planner Agent다.사용자 요청:"간단한 챗봇 CRUD 만들어서 로컬 서버에 띄워줘"현재 정책:- 파일 읽기는 자동 가능- 파일 생성/수정은 승인 필요- 서버 실행은 승인 필요- 외부 API 호출은 승인 필요- secret 접근 금지- sandbox workspace 밖 접근 금지해야 할 일:1. 작업 계획 생성2. 필요한 기술스택 제안3. 자동 실행 가능한 단계와 승인 필요한 단계 분리4. Worker에게 넘길 실행 계획 JSON 생성
```

OpenClaw의 답변은 예를 들어 이렇게 나와야 해.

```
{  "summary": "FastAPI 기반 간단한 챗봇 CRUD 서버를 생성하고 로컬에서 실행합니다.",  "stack": {    "language": "python",    "framework": "fastapi",    "server": "uvicorn",    "storage": "in-memory"  },  "steps": [    {      "step": 1,      "name": "create_workspace",      "description": "sandbox workspace에 chatbot-crud 프로젝트 디렉토리를 생성합니다.",      "requires_approval": false    },    {      "step": 2,      "name": "write_files",      "description": "main.py, requirements.txt를 생성합니다.",      "requires_approval": true    },    {      "step": 3,      "name": "install_dependencies",      "description": "fastapi와 uvicorn을 설치합니다.",      "requires_approval": true    },    {      "step": 4,      "name": "run_server",      "description": "uvicorn으로 로컬 서버를 실행합니다.",      "requires_approval": true    },    {      "step": 5,      "name": "health_check",      "description": "서버가 정상 실행되는지 curl로 확인합니다.",      "requires_approval": false    }  ],  "approval_required": true,  "approval_reason": "파일 생성, 패키지 설치, 로컬 서버 실행이 포함되어 있습니다."}
```

이 단계에서 OpenClaw는 **실행하지 않고 계획만 세움**.

---

## Step 4. Orchestrator가 승인 요청 생성

OpenClaw가 계획을 만들면, Orchestrator는 task를 생성함.

```
{  "task_id": "task_20260530_001",  "status": "waiting_approval",  "request": "간단한 챗봇 CRUD 만들어서 로컬 서버에 띄워줘",  "requires_approval": true,  "plan": [...]}
```

그리고 Telegram에 이렇게 보냄.

```
작업 계획을 생성했습니다.작업 ID: task_20260530_001수행 예정:1. FastAPI 프로젝트 생성2. main.py / requirements.txt 생성3. dependency 설치4. uvicorn 서버 실행5. health check승인 필요:- 파일 생성- 패키지 설치- 로컬 서버 실행승인하려면:/approve task_20260530_001
```

여기까지가 1차 사이클.

```
사용자 요청→ LLM이 계획 생성→ 승인 요청
```

---

# 6. 사용자가 승인하면

사용자가 Telegram에 입력.

```
/approve task_20260530_001
```

이건 일반 텍스트가 아니라 command로 처리됨.

```
bot.py→ /approve handler→ Orchestrator /approve API
```

Orchestrator는 확인함.

```
- 이 사용자가 승인 권한이 있는가?- 해당 task가 대기 상태인가?- 승인 가능한 작업인가?
```

문제 없으면:

```
{  "task_id": "task_20260530_001",  "status": "approved"}
```

그리고 Worker 실행으로 넘어감.

---

# 7. Worker가 실제 작업 실행

이제 실제 손발은 Worker가 담당해.

```
Orchestrator→ Worker API
```

예를 들어 Worker가 실행할 작업은 이런 것.

```
/workspaces/tasks/task_20260530_001/chatbot-crud
```

파일 생성:

```
main.pyrequirements.txt
```

`main.py` 예시:

```
from fastapi import FastAPI, HTTPExceptionfrom pydantic import BaseModelfrom uuid import uuid4app = FastAPI(title="Simple Chatbot CRUD")class ChatbotCreateRequest(BaseModel):    name: str    description: strclass ChatbotUpdateRequest(BaseModel):    name: str | None = None    description: str | None = Nonechatbots = {}@app.get("/health")def health():    return {"status": "ok"}@app.post("/chatbots")def create_chatbot(request: ChatbotCreateRequest):    chatbot_id = str(uuid4())    chatbots[chatbot_id] = {        "id": chatbot_id,        "name": request.name,        "description": request.description,    }    return chatbots[chatbot_id]@app.get("/chatbots")def list_chatbots():    return list(chatbots.values())@app.get("/chatbots/{chatbot_id}")def get_chatbot(chatbot_id: str):    if chatbot_id not in chatbots:        raise HTTPException(status_code=404, detail="Chatbot not found")    return chatbots[chatbot_id]@app.patch("/chatbots/{chatbot_id}")def update_chatbot(chatbot_id: str, request: ChatbotUpdateRequest):    if chatbot_id not in chatbots:        raise HTTPException(status_code=404, detail="Chatbot not found")    if request.name is not None:        chatbots[chatbot_id]["name"] = request.name    if request.description is not None:        chatbots[chatbot_id]["description"] = request.description    return chatbots[chatbot_id]@app.delete("/chatbots/{chatbot_id}")def delete_chatbot(chatbot_id: str):    if chatbot_id not in chatbots:        raise HTTPException(status_code=404, detail="Chatbot not found")    deleted = chatbots.pop(chatbot_id)    return {        "deleted": True,        "chatbot": deleted,    }
```

`requirements.txt`:

```
fastapiuvicornpydantic
```

서버 실행:

```
uvicorn main:app --host 0.0.0.0 --port 18001
```

health check:

```
curl http://127.0.0.1:18001/health
```

성공하면:

```
{  "status": "ok"}
```

# 8. 여기서 LLM 호출은 몇 번 일어나냐

중요한 질문이 이거야.

이 작업에서 LLM은 한 번만 호출되는 게 아니야.  
최종 구조에서는 여러 번 호출될 수 있어.

## LLM 호출 1: 작업 분류/계획

```
사용자 요청을 보고 무엇을 해야 하는지 계획
```

담당:

```
OpenClaw Planner Agent
```

---

## LLM 호출 2: 코드 생성

```
FastAPI CRUD 코드를 생성
```

담당:

```
OpenClaw Code Agent 또는 Orchestrator /generate
```

---

## LLM 호출 3: 실행 로그 분석

서버 실행 중 에러가 날 수 있음.

예:

```
ModuleNotFoundError: No module named 'fastapi'
```

이때 Worker가 로그를 반환하면, OpenClaw가 분석함.

```
에러 원인은 fastapi 패키지가 설치되지 않았기 때문입니다.requirements.txt 설치 단계가 필요합니다.
```

---

## LLM 호출 4: 결과 요약

마지막으로 사용자에게 보고할 메시지를 생성함.

```
작업 완료했습니다.- FastAPI CRUD 서버 생성- 포트: 18001- health check 성공- 테스트 가능한 API:  GET /health  POST /chatbots  GET /chatbots  GET /chatbots/{id}  PATCH /chatbots/{id}  DELETE /chatbots/{id}
```

# 10. 각 컴포넌트의 책임

## `bot.py` 또는 Gateway

```
- Telegram 메시지 받기- /approve 같은 명령어 파싱- 사용자 ID 전달- 결과를 Telegram에 다시 보내기
```

하지 말아야 할 것:

```
- 직접 파일 생성- 직접 서버 실행- 직접 GitHub push- 직접 위험 작업 판단
```

---

## Orchestrator

```
- 이 요청이 어떤 작업인지 분류- task_id 생성- 승인 필요 여부 판단- OpenClaw 호출- Worker 호출- 상태 저장- audit log 저장
```

---

## OpenClaw

```
- 작업 계획 생성- 코드 초안 생성- 실행 결과 분석- 실패 로그 해석- 사용자 보고문 생성
```

직접 하면 안 되는 것:

```
- 운영 서버에서 직접 명령 실행- 승인 없이 파일 수정- 승인 없이 서버 실행
```

---

## Worker

```
- sandbox workspace 생성- 파일 쓰기- dependency 설치- 서버 실행- 테스트 실행- 결과 로그 반환
```

---

## Ollama / LLM

```
- OpenClaw 또는 Orchestrator가 준 prompt에 따라 텍스트 생성- 코드 생성- 계획 생성- 로그 분석
```

# 13. 지금 네 질문에 대한 핵심 답

> LLM을 호출하는 사이클이 어떻게 되는 거야?

이 요청에서는 LLM이 이렇게 호출됨.

```
1차 LLM 호출:사용자 요청을 분석해서 작업 계획 생성2차 LLM 호출:필요한 코드 생성3차 LLM 호출:Worker 실행 결과나 에러 로그 분석4차 LLM 호출:사용자에게 보낼 완료 보고문 생성
```

하지만 중요한 건, LLM이 직접 실행하지 않는다는 것.

```
LLM / OpenClaw:무엇을 할지 생각하고 코드/계획을 생성Orchestrator:해도 되는지 판단하고 승인 상태를 관리Worker:실제로 파일 만들고 서버 띄움
```

---

# 14. 최종 한 줄

```
“간단한 챗봇 CRUD 만들어서 로컬 서버에 띄워줘”라는 요청이 오면, OpenClaw/LLM은 작업 계획과 코드 생성·로그 해석을 담당하고, Orchestrator는 승인/정책/상태 관리를 담당하며, Worker가 승인된 범위 안에서 실제 파일 생성·서버 실행을 수행하는 사이클로 가야 한다.
```
